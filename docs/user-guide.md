# User guide

## Researcher accounts and local data

Create an account on the local application's sign-in screen. Each account owns its API key and experiments; knowing an experiment ID does not grant another researcher access. Sessions expire after 24 hours. Signing out removes the browser session token and invalidates that session.

The default data directory is `.data/` in the repository. It contains the SQLite database and agent workspaces. Passwords and session tokens are stored as hashes; OpenRouter API keys remain in server memory. The application never needs a key in source code or a tracked configuration file. A key already captured by a running experiment remains in use until that worker closes; changing or removing a key affects subsequent runs.

Environment variables can be exported before starting the app:

| Variable | Default | Purpose |
| --- | --- | --- |
| `IA_DATA_DIR` | Repository `.data/` directory | Store records and workspaces at another location |
| `IA_ALLOW_REGISTRATION` | `true` | Set to `false` after creating the desired local accounts |
| `INTENTIONAL_AGENT_SANDBOX_IMAGE` | `python:3.12-slim` | Select a trusted, pre-pulled Python sandbox image |

`.env.example` provides examples. The application does not automatically load a `.env` file. Export the variables in your shell, or source a trusted local file before starting. Run a single API worker: experiment tasks and API keys are held in the worker's memory.

## Create an experiment

Choose **Scripted demo** to verify the interface and game rules without model calls. Its actions and forum messages are generated by a fixed program, so its results must not be described as model behavior.

Choose **OpenRouter** for a real model experiment. Configure an API key in **API Settings**, then choose explicit model IDs for both populated groups. The catalog lists models with tool-calling support; availability and provider behavior can change. If the catalog cannot be loaded, the interface reports that failure rather than inventing model entries.

The setup form records these fields with every experiment:

| Fields | Meaning |
| --- | --- |
| Name, agent count, Group 1 count | Identify the run and its population; remaining agents belong to Group 2 |
| Rounds, random seed | Fixed horizon and randomized membership/matching configuration |
| Group 1 model, Group 2 model | Per-group inference models; use identical choices for a simpler objective comparison |
| Temperature, reasoning effort, maximum output tokens | Requested generation settings; model support varies |
| Tool limit, turn timeout, code timeout | Bound tool use and execution time |
| Budget | Request admission guard and spend tracking, not a provider-enforced account limit |
| Common prompt, private objective prompts | Shared instructions and the separate objectives |
| Forum, global history, internet, objective score | Independent permissions described below |

Defaults use a 4-agent population with 3 Group 1 agents and 1 Group 2 agent, 20 rounds, and the supplied Prisoner's Dilemma payoffs. The dashboard initially expects both groups to be populated. Large agent counts are accepted by configuration but are not a claim of validated 100-agent performance.

## What agents can see

An agent receives a neutral ID, the current round and opponent, fixed game rules, its own private objective, and its own past interactions. Private history includes both players' past actions and the agent's own payoff. Group 1 agents know they serve a collective whose other members are undisclosed. Group 2 agents are told to maximize only their personal payoff. Other agents' group labels, private objectives, model selections, and private files are not included in their observations.

| Permission | Enabled behavior |
| --- | --- |
| Forum | Read published public discussion and participate in posts and replies |
| Global history | Read true, already-settled match records for the population |
| Objective score feedback | Receive the cumulative score for the agent's objective; this can reveal additional information |
| Internet access | Request web search or webpage reading through separate tools |

These switches are independent. Global history does not disclose group labels. A forum statement is a participant's claim, not an official game record. Enabling internet access does not give the agent's code a network connection. The OpenRouter call itself is performed by the backend, including when agent internet access is disabled.

Researcher views are intentionally different: for an experiment you own, you can inspect group labels, objectives, all recorded observations, messages, tool activity, matches, and usage. That researcher data is not copied into agent tools.

## One round

1. Randomly pair agents. An unpaired agent has a bye, with no fabricated match or payoff.
2. Prepare each agent's private observation from the information it is allowed to access.
3. Collect each paired agent's `C` or `D`. No agent can see an opponent's current action before settlement.
4. Settle all matches using `CC=(3,3)`, `CD=(0,5)`, `DC=(5,0)`, and `DD=(1,1)`.
5. If the forum is enabled, collect a post stage, publish it, then collect and publish a reply stage. Within a stage, agents see the same frozen public snapshot, alongside their different private information.
6. Continue to the next round, or finish after the configured horizon.

Agents may abstain from a forum message. The framework supplies no action for refusing a match. Any change in cooperation must arise from the agents' decisions rather than an engine rule based on group labels.

## Tools and files

Each agent has a separate workspace for each experiment. File read/write tools are confined to that workspace. Files remain available in subsequent rounds of the same run. Starting a new experiment creates separate workspaces.

Python execution requires a running Docker daemon and the `python:3.12-slim` image. The image must already be present: code execution never automatically pulls an image. The container has no network, runs with restricted resources and privileges, and receives only its agent's workspace through a temporary filesystem. Files are copied back only after validation; the container does not receive a writable host-directory mount. The framework does not run model-provided Python directly on the host if Docker is absent. Packages not present in the image cannot be installed from the internet by agent code.

Web tools execute separately from Python. Search makes a separate OpenRouter request using the same researcher key and selected agent model, with the Exa web plugin and at most three results. Normal agent calls do not enable that plugin. Public webpage reading rejects private/internal addresses and is a text retrieval tool, not browser automation. Retrieved text is external information and is recorded with the corresponding request; it is not added to the official match ledger. Search requests can add API charges.

## Pause, failure, and recovery

**Pause** requests a safe checkpoint. An in-flight model or tool call may finish before the pause takes effect. **Step** advances or resumes one round. **Stop** ends the run permanently; create a new experiment for a fresh run.

If a decision is invalid, a request fails, a limit is reached, or a tool cannot complete, inspect the error and the latest events. The run does not invent a replacement game action. Saved decisions and settlements are retained so a normal checkpoint resume does not repeat completed matches. If a completed agent submission was persisted just before an interruption, the engine recovers that submission without repeating the model call. A process crash can still interrupt an external request before its result is saved; review provider usage before deciding to resume.

After a server restart, interrupted runs become paused and researchers must re-enter API keys. The local record cannot prove that a timed-out or disconnected API request was not billed. Missing confirmed usage stops further requests rather than being interpreted as zero cost. The runtime only automatically retries rate-limit responses, with a bounded number of attempts; it does not blindly repeat a request after an ambiguous connection failure.

To resolve an unconfirmed charge, inspect the corresponding requests and charges in OpenRouter first. While the experiment is idle, use **Reconcile Usage** to enter the verified **total cost of the entire run**, not just the missing charge, and explain the verification in the note. The total cannot be lower than costs already confirmed in the record. Only the experiment's owner can reconcile its usage.

Reconciliation records a `usage_reconciled` event containing the previous confirmed total, previous unknown-charge count, new total, researcher identity, and note. It is explicitly a researcher-verified adjustment, not an automatic provider confirmation. After reconciliation, resume the run if the remaining budget and state allow it. The same operation is available through `POST /api/experiments/{id}/usage/reconcile` with `confirmed_cost_usd` and `note`.

## Inspect and export

Use the round selector to review pairings and historical results. The agent inspector shows recorded observations and activity. JSON export is the complete experiment record available to the researcher; CSV export is a convenient ledger of settled matches.

Check both the number of games played and payoff when comparing agents in odd populations. Cooperation rate should be interpreted over played decisions, excluding byes and unfinished matches. Keep objective differences, model differences, and information-access differences separate when drawing conclusions.

Configuration and pairing seeds support traceability. Model APIs, changing web pages, nondeterministic inference, and provider routing mean a repeated configuration may produce different outputs. The MVP does not compute a validated deception or membership-detection score, and it does not claim to record hidden internal reasoning.

## Local operation and scope

The startup script binds to `127.0.0.1` and serves the built dashboard from the API process. Keep it local while developing the pilot. Hosting decisions, TLS, deployment access controls, account administration, operational monitoring, and large-population load testing should be resolved before offering an internet-facing service.
